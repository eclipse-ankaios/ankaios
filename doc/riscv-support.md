# RISC-V support: implementation plan and acceptance criteria

This document proposes a concrete path for adding RISC-V support to Ankaios. It is intentionally a design and acceptance document: it does not claim that a RISC-V build or test run has already succeeded.

Related issue: [Support RISC-V architecture](https://github.com/eclipse-ankaios/ankaios/issues/786).

## Scope and target

The primary target proposed for the first implementation is `riscv64gc-unknown-linux-musl`. A musl target gives the release pipeline a clear, reproducible contract for static or minimally dynamic artifacts and is suitable for both QEMU-based validation and boards such as the StarFive VisionFive 2.

The host-native build must remain separate from the RISC-V cross-build. The support matrix should make the target explicit rather than silently selecting a linker from the runner environment. Whether `riscv64gc-unknown-linux-gnu` is also required should be an explicit maintainer decision, documented before adding a second release family.

## Development environment

The dev container should install the Rust target through the repository's existing toolchain mechanism and provide the matching RISC-V linker, binutils, C headers and musl development files. Package names should follow the container distribution instead of being copied between images. The setup must be reproducible from a fresh container and must not require tools installed on a developer's host.

A short environment check should print the selected Rust target, linker and binutils versions. This is diagnostic output only; it should not be used as a security or compatibility claim.

## CI design

The first CI stage should cross-compile the workspace for `riscv64gc-unknown-linux-musl` and run checks that do not require target execution. A QEMU job can then execute the smallest deterministic smoke path. If a maintained native RISC-V runner becomes available, it should be an additional job rather than silently replacing the QEMU path.

The workflow should expose the architecture in its job name and artifact metadata. Failures in target installation, linking and execution should remain distinguishable so that a missing toolchain is not reported as an application regression.

## Release artifacts

RISC-V artifacts should include the exact target triple in their filename, for example `ankaios-<version>-riscv64gc-unknown-linux-musl`. Each artifact should have a checksum generated by the existing release process. The release notes should state whether the artifact was cross-compiled, executed under QEMU, or exercised on native hardware.

## Acceptance criteria

- The dev container installs the target and its linker from a clean setup.
- CI produces a RISC-V build without changing the host build.
- Unit or integration checks that can run under QEMU are executed there.
- At least one deterministic startup or CLI smoke path is covered.
- Release artifacts and checksums contain an unambiguous target triple.
- The documentation explains the VisionFive 2 and QEMU paths, including known limitations.
- The workflow logs preserve enough toolchain information to reproduce a failure.

## Open decisions for maintainers

1. Which runner label and QEMU version are supported by the project policy?
2. Should the first release artifact be musl-only, or should GNU libc be supported too?
3. Which Ankaios components are in scope for the first target, and which depend on unavailable native libraries?
4. Which smoke path is stable enough to become the compatibility gate?

Once these decisions are accepted, the implementation can be split into focused changes for the container, CI, release packaging and hardware documentation. This PR contributes the shared design and review checklist; no new installation, compilation or test execution was performed in this browser-only contribution session.
